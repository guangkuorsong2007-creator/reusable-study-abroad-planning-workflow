## What actually drove progress / 实际推进机制

| Step | Input or trigger | Work performed | Result and feedback |
| --- | --- | --- | --- |
| 1. Open-ended setup | User asks for undergraduate/postgraduate planning and how an agent could help | Broad intake and project setup | Initial facts, collaboration preferences and permission to save locally |
| 2. Personal evidence | User supplies transcripts/curriculum and substantial answers | Local reading, grade/curriculum extraction, questions about unclear figures | Profile and academic baseline; incomplete rules kept open |
| 3. Early advice and correction | Initial advice emphasizes academic recovery and broad Canadian examples | User rejects study-method focus and clarifies ranking preference | Scope changes to programs and strategic preparation; research order changes |
| 4. External research and narrowing | Admissions questions and Alberta interest | Program-specific official-source research, detailed interview, course-fit mapping | Program families and prerequisite gaps; recommendations remain conditional |
| 5. Cross-tool divergence | Two workspaces hold overlapping, conflicting work | Compare files, expose conflicts, ask user about actual preferences, preserve history | One canonical workspace and shared recording protocol |
| 6. Specific route and target | User chooses Alberta and clarifies assessed-GPA aspiration | Actual registration/scale evidence, proposed courses, scenario calculation | Detailed bilingual proposal plus machine-readable inputs |
| 7. Independent comparison | User wants competing proposals evaluated | Recalculation and comparative report | Arithmetic agreement, but later review qualifies overconfident feasibility language |
| 8. Retrospective | User asks what was accomplished and how to improve the method | Separate outputs, user choices, assumptions and real-world outcomes | Current process-design discussion |

This was an iterative process in which the user's questions and corrections were essential. Some preference changes reflect useful discovery rather than preventable mistakes. Improvement should reduce avoidable rework without demanding that a person know every preference before exploration.

## Failure mechanisms and targeted improvements / 返工机制与改法

| Observed mechanism | Why it mattered | Proposed change |
| --- | --- | --- |
| Broad research before a few decisive tradeoffs were clear | Rankings, settlement goals and subject/format choices changed the relevant comparison | Establish a short decision brief; label unresolved preferences; do small exploratory comparisons before extensive research |
| Questions mixed urgent decisions with low-impact details | A future academic calendar or study routine did not always help the current choice | For each question identify which decision it could change; defer the rest |
| Different grade subsets shared the same label | Correct arithmetic on one subset could be misrepresented as the student's official GPA | Define metric, course set, weight, time window, attempt handling, source and achieved/target status before calculation |
| Model outputs acquired excessive authority | Arbitrary conversions and proposed grades could become apparent eligibility | Keep assumptions visible and link each important output to inputs/rules; unknown conversion stays unknown |
| Different clients maintained different active state | Conflicting priorities, old final plans and repeated intake | One current case record; capability-dependent handoff; separate immutable-ish history from current state |
| Independent review became an overall verdict | Reproducing arithmetic does not validate feasibility or policy applicability | Review claims separately: input accuracy, arithmetic, rule applicability, workload, user fit, outcome language |
| Detail expanded beyond the user's current request | Daily coaching displaced school/preparation planning | State the current decision and excluded topics at the beginning of each work unit |
| Long reports disguised unfinished real-world tasks | Documents and model targets could look like achieved progress | Keep work status separate from evidence status and external execution status |

## Reusable architecture / 可复用结构

Use four separable components. None should silently carry this person's private data or Canada-specific assumptions into another case.

1. **Common process / 通用流程:** goal clarification, evidence handling, exploration, comparison, user decisions, actions, review, handoff. Includes permission boundaries and evidence vocabulary.
2. **Person/case record / 个案档案:** priorities, constraints, family/funding conditions, actual qualifications, interests, language, deadlines and tolerance for uncertainty. Unknown and not-yet-decided are valid values. Different people require isolated case workspaces.
3. **Destination/rule record / 国家地区规则:** jurisdiction, institution/program, applicant category, assessment basis, relevant pathway stages, official evidence, publication/access/effective dates and unresolved applicability. A destination can have multiple subnational/occupational branches; missing stages or routes remain explicitly unavailable/unknown. Never assume every country has a study-to-permanent-status path.
4. **Tool capability record / 工具能力:** can the current environment persist files, read documents/images, retrieve official sources, run arithmetic, and support review? Record tested capabilities and fallbacks, not claims based on a brand name.

One capable agent may perform the roles sequentially. Multiple agents are optional, not the definition of quality. A reviewer needs primary inputs and a precise claim to check; another model repeating a conclusion is weak evidence. Parallel writers must not update the same active state.

A chat-only environment can use a user-approved, sanitized state export/import instead of shared files. File-capable environments can use local state. Missing browsing means rule-dependent conclusions stay provisional; missing execution means arithmetic is shown transparently or handed off for calculation. Do not imply a prompt can create persistence, browsing or automatic recording in every tool. Verify actual handoff with a harmless sample before relying on it.

## Proposed work cycle and completion criteria / 阶段与完成标准

| Stage | Smallest useful output | Condition for advancing the relevant claim |
| --- | --- | --- |
| 0. Establish collaboration | Scope, audience, language, storage/capabilities, privacy and action permissions | Know what the environment can actually do; keep case data separate |
| 1. Frame today's decision | Decision to make, priority order, hard constraints, flexible preferences and unknowns | User understands the tradeoff; no need to settle all life goals |
| 2. Establish minimum evidence | Relevant records, metric definitions, timeline and funding facts | Major recommendation-changing conflicts resolved or explicitly bracketed |
| 3. Explore alternatives | A small, diverse set of plausible route/program families and disqualifiers | Explain why these options deserve deeper work; keep exploration distinct from eligibility |
| 4. Verify consequential rules | Claim-by-claim official evidence with applicability/dates | Support any eligibility or cost claim at the level it is stated |
| 5. Compare choices | Tradeoff table, known blockers, uncertainty scenarios and reversible preparations | No invented probabilities or opaque composite score disguising an unknown hard condition |
| 6. Decide and prepare | User choice, rationale, open alternatives and next evidence-producing actions | Choice actually accepted; actions have a clear output and dependency |
| 7. Review and continue | Scoped review, changed facts, stale conclusions, concise checkpoint | Reviewer can reproduce consequential calculations and next session can resume correctly |

These are checks on conclusions, not bureaucratic reasons to halt all work. Unknown GPA conversion can block an eligibility claim while course mapping and program exploration continue. Stronger evidence is needed before a costly/irreversible commitment than before generating a candidate option. External contact, uploads, applications, purchases or scheduled automation require their own authorization; routine authorized local documentation does not.

Research should be driven by a decision: ask what finding would change the next choice. Stop expanding when the relevant options/tradeoffs are adequately supported for that decision and remaining uncertainty is explicit. If one unresolved rule changes the preferred route, prioritize it or compare both scenarios. If no accessible source resolves it, record the blocker and the specific question for an authorized institutional inquiry; never fill it with a guessed probability.

## Asking better questions / 提问方式

Begin with facts needed for the immediate decision and explain unfamiliar concepts before asking the person to choose. Use concrete tradeoffs when preferences are unclear: compare two plausible weeks of work or two budget/time scenarios rather than demanding a definitive career identity.

Use a few related questions per round, explain why the answer matters, and consult saved evidence first. “I don't know yet” should trigger exploration, not repeated pressure. Distinguish user-preference conflict (the user decides) from conflicting factual evidence (investigate documents/rules) and source-policy conflict (check scope, applicable authority and effective dates).

A preparation action should work across several still-plausible options when possible. Evidence from a small work sample can clarify subject fit. This is an optional method for the relevant person, not a universal requirement or a revival of this user's deferred daily study coaching.

## Keeping state usable / 状态与接续

Maintain one authoritative current value for each field. Decision history records changes; current records carry a pointer and date rather than duplicating long contradictory summaries. Keep status short: present task, last substantive result, pending question, next useful step, evidence limitations and location of detail.

Every work unit ends with a short human-readable delta: what changed, what is still unknown and what happens next. Update only the relevant records; log a substantive result or “no substantive change” rather than rewriting all documents. Save during long work after a meaningful intermediate result. A Markdown instruction is not a lock or an interruption-recovery guarantee.

For calculated/researched conclusions, preserve simple dependencies: conclusion -> relevant inputs, rule/source IDs, assumptions and calculation version. When a grade, budget, priority or policy changes, identify the affected conclusions as needing review. Do not invalidate every unrelated topic or run a broad research cycle automatically.

Knowledge maintenance can be event-driven: a new transcript, changed goal, changed source, offer or impending commitment prompts a relevant check. Any background reminder/monitor is a separate user choice. Avoid a universal fixed expiry period; sources differ in volatility and consequences.

## Validation before calling the process reusable / 复用前验证

The current project is one case from which to learn. It does not validate a universal workflow. Proposed first version: a plain-language guide, blank case templates, small task prompts, rule-evidence templates, calculation conventions and an acceptance checklist. Skill packaging or a product can follow once audience/form/scope are chosen. These are recommendations, not selected deliverables.

Suggested synthetic/manual trial cases:

- A student with an unspecified destination and uncertain career interests: avoid premature national assumptions and large intake questionnaires.
- A working adult or caregiver with a fixed budget and a regulated occupation: reveal constraints that a student-only process misses.
- A destination with a materially different education/work/residence structure: test whether the process leaves unsupported transitions open rather than importing Canadian stages or thresholds.
- A fresh agent receiving a checkpoint: identify the current task, confirmed facts, unresolved questions and next action without repeated intake; disclose unsupported capabilities.
- A new policy or grade update: mark only affected conclusions for review and preserve actual/target and local/foreign distinctions.

The original proposed trial list has not been fully executed as separate cases. One integrated guided SYN-UG-101 internal trial has now covered open preferences, conflicting metrics, fresh-subagent handoff and changed inputs; see the execution note below. Other cases and external environments remain untested. No personal documents should be put into public examples. Use synthetic fixtures or separately consented de-identified inputs.

Evaluate by: unnecessary repeated questions; untraceable important claims; unsupported eligibility assertions; incompatible current-state fields; missed dependencies after a change; ability to resume in a fresh environment; user understanding of tradeoffs; and time/tool/token effort required to reach a usable decision. Baselines are not yet measured. Fewer messages or faster answers alone do not prove better planning.

## Product implications of the confirmed direction / 已确认方向的设计含义

**User decisions:** individual-first while supporting advisers later; eventual product/service; full-chain, multiple-destination scope. These set direction without selecting a software platform, business model, price, launch date or implementation authorization.

**Assistant proposal: design the entire journey and validate one bounded part first.** The first useful result could be a clear starting assessment, a defensible comparison of a manageable set of route families, key unresolved conditions, a preparation plan and a checkpoint that another session can use. Actual admission, work and residence results require later evidence; describe their dependencies throughout the journey without pretending to complete them in one report.

Proposed individual journey:

| User experience | Behind-the-scenes work | Tangible result |
| --- | --- | --- |
| Explain what they want and what is unclear | Adaptive interview, distinguish priorities/constraints and explore unfamiliar choices | A short user-confirmed decision brief |
| Provide only relevant records | Local/private extraction where available, conflict checking and definitions | An attributable factual baseline and precise missing information |
| Compare countries/regions at an appropriate depth | Broad route feasibility screening, then focused institution/program/occupation research | Comparable tradeoffs with evidence dates and unknowns |
| Choose a current direction while retaining useful options | Separate hard blockers, user preferences and uncertain future conditions | Decision rationale and conditions for revisiting it |
| Prepare and return with new information | Evidence-producing actions; targeted update of affected conclusions | Next actions, dependencies and a resumable state |

The first population can be narrow while the underlying structure supports broader cases. A student-focused trial does not establish suitability for workers, families or regulated professions. The full chain should remain visible even when one component is investigated in depth.

Reusable public rule knowledge and private case data should be stored separately. A shared source may be reusable only after its date, applicant category and applicability are checked. One person's preferences, documents and assessed outcomes do not automatically transfer. Adviser use should eventually support explicit access and decision responsibilities rather than silently broadening data sharing.

Research effort is a design concern: begin with destination/route families, narrow with meaningful constraints and preferences, then deepen the plausible options. Comparing every program in every country is neither necessary nor a reliable completion criterion. Important unknown conditions must remain visible instead of being hidden inside an invented overall score.

The enduring service value proposed here is traceable decisions, focused preparation and reliable updates across tools. A single long generated report is only one possible artifact. Whether users value this and can use it successfully still needs validation; no market-demand or commercial-readiness claim is made.
